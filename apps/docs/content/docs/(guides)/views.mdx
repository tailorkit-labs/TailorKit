---
title: Views and slots
description: Publish layered host context and render one app view per slot.
---

A host **view** describes the current situation, such as `/users/detail`, and
its **context** is the data the host supplies. A **slot** is a place where the
host renders an app. An app **view** is the implementation selected for that
slot and host view.

TailorKit does not inspect the browser URL. Paths describe a hierarchy that the
host publishes explicitly.

## Define the host contract

```ts
import { createTailorKit } from "tailorkit";
import { z } from "zod";

export const tailorKit = createTailorKit({
  components: {},
  scopes: { user: z.object({ userId: z.string().min(1) }) },
  slots: { navbar: { views: ["/"] }, panel: { views: ["/users", "/users/detail"] } },
  views: {
    "/": z.object({ workspaceId: z.string() }),
    "/users": z.object({ canManageUsers: z.boolean() }),
    "/users/detail": z.object({ user: userSchema }),
  },
});
```

Context schemas must describe objects with named fields, not scalar values or
arrays. An optional object context may be omitted; it contributes no fields.
Each view declares only its own fields. Ancestor fields are composed into the
context received by app views. A field must have one owning view: duplicate
field names across ancestors are rejected by the type checker and runtime.

## Name multiple installation scopes

Give each identity boundary its own schema key. Return values under those same
keys from `authenticate()`, then select the identities for each app read:

```ts
import { createTailorKit } from "tailorkit";
import { auth } from "#lib/auth";
import { z } from "zod";

export const tailorKit = createTailorKit({
  components: {},
  scopes: {
    org: z.object({ orgId: z.string() }),
    userOrg: z.object({ orgId: z.string(), userId: z.string() }),
  },
  // views and slots can be added here.
});

async function handleRequest(request: Request) {
  return tailorKit.handler(request, {
    authenticate: async () => {
      const session = await auth(request);
      if (!session) return null;

      return {
        scopes: {
          org: { orgId: session.org.id },
          userOrg: { orgId: session.org.id, userId: session.user.id },
        },
      };
    },
  });
}
```

```tsx
import { createTailorKitClient, Root } from "tailorkit/react";
import type { tailorKit } from "./tailorkit";

export const client = createTailorKitClient<typeof tailorKit>({
  baseUrl: "https://example.com/api/tailorkit/",
});

const { useApps } = client;

function InstalledApps() {
  const { data: apps, isLoading } = useApps({ scopes: ["org", "userOrg"] });
  if (isLoading) return <p>Loading apps…</p>;
  return (
    <ul>
      {apps?.map((app) => (
        <li key={app.id}>{app.name}</li>
      ))}
    </ul>
  );
}

export function InstalledAppsRoot() {
  return (
    <Root client={client}>
      <InstalledApps />
    </Root>
  );
}
```

Scope values identify installations exactly, so keep them to stable identity
data such as opaque IDs. Do not include mutable settings or feature lists:
changing any value changes the installation identity. Nested objects and arrays
are supported; TailorKit sorts object keys recursively, so property insertion
order does not change identity, while array order remains significant.

## Configure React once

```tsx title="./src/lib/tailorkit-client.tsx"
import { createTailorKitClient } from "tailorkit/react";
import type { tailorKit } from "./tailorkit";

export const client = createTailorKitClient<typeof tailorKit>({
  baseUrl: "https://example.com/api/tailorkit/",
});

export const { Slot, useApps, useViews, useRegisterView } = client;
```

The helpers carry the view and slot types from the client. Import `Root` from
`tailorkit/react` and pass it the client; use `useApps`, `useRegisterView`, and
`Slot` beneath it. Each root owns an independent registry, even when roots
share a client. Separate clients can expose different view and slot contracts
in the same TypeScript project.
The bound `useApps` also types `scopes` from the server schema. Pass names to
select which authenticated identities to list. Calling `useApps()` with no
options loads every scope returned by `authenticate()`. Passing `scopes: []`
loads no apps.

```tsx
import { Root } from "tailorkit/react";
import { Slot, client } from "./tailorkit-client";

function Host({ app, children }) {
  return (
    <Root client={client}>
      <nav>
        <Slot app={app} name="navbar" />
      </nav>
      <main>{children}</main>
      <aside>
        <Slot app={app} name="panel" />
      </aside>
    </Root>
  );
}
```

Use the exported `useApps()` below `Root` to load installed apps. For a
supplied app list, pass `apps` to `Root`; the hook returns that list without
fetching. Updates to the list are reflected in the hook, and removing the prop
resumes discovery.

## List app views

Use `useViews()` to list the views implemented by installed apps:

```tsx
const {
  data: views,
  isPending,
  error,
  refetch,
} = useViews({
  scopes: ["org"],
  appIds: ["app-id"],
  slot: "panel",
});
```

All filters are optional. Values within a filter match any entry; different
filters must all match. An empty `scopes` or `appIds` array returns no entries.
Each view has a stable `id`, its `app`, a `slot`, and its declared `path`.
Disabled entries (`false`) are excluded.

`useApps` and `useViews` share one authenticated `/apps` request per `Root`.
Filtering happens locally; changing filters does not fetch again. `refetch()`
refreshes both hooks. After a session change, refresh discovery or remount `Root`.
Supplied `Root` apps must include `views` metadata to appear in `useViews`.
Rebuild and redeploy older apps to publish this metadata.

## Publish each layer

Call `useRegisterView` in the layout or page that owns the data:

```tsx
import { useRegisterView } from "./tailorkit-client";

function WorkspaceLayout({ workspaceId }) {
  useRegisterView("/", { context: { workspaceId } });
  return <Outlet />;
}

function UsersLayout({ canManageUsers }) {
  useRegisterView("/users", { context: { canManageUsers } });
  return <Outlet />;
}

function UserDetail({ user }) {
  useRegisterView("/users/detail", { context: { user } });
  return <UserDetails user={user} />;
}
```

The deepest mounted view is current. Only its ancestors contribute context.
Unmounting detail returns to the parent view. Register one active route branch
per root; unrelated simultaneous branches are ambiguous.

Every declared ancestor must be mounted to render a descendant view. A missing
ancestor produces the selected view's error state rather than partial context.
Undeclared intermediate path segments do not require registrations.

## Implement views per slot

```tsx
const detail = createView("/users/detail", { component: UserTools });

function UserTools() {
  const { workspaceId, canManageUsers, user } = detail.useContext();
  return <UserActions user={user} canManageUsers={canManageUsers} />;
}

export default defineClient({
  slots: {
    navbar: { "/": navigation },
    panel: {
      "/users": generalUserTools,
      "/users/detail": detail,
    },
  },
});
```

On `/users/detail`, the navbar renders `navigation` and the panel renders
`detail`. The panel does not also render `generalUserTools`. Parent contexts
compose; parent components do not.

Each slot searches the active path, then its ancestors, considering only
paths in its supported `views` list. A supported ancestor remains eligible when
the current, more specific view is not supported.
Fallback never crosses slot boundaries. An empty supported view list disables
all views in that slot. View lists are typed from the configured client schema;
app bindings and explicit `Slot.Controlled` views are restricted to the selected slot.

Supported lists control view implementations, not context inheritance. For
example, the panel's `/users` view still receives `workspaceId` from `/`, even
though `/` is not a supported panel view. An unsupported slot or unmatched
view renders nothing. Set a view entry to `false` to explicitly stop fallback:

```tsx
panel: { "/users": generalTools, "/users/detail": false }
```

## Loading and errors

Keep the view registered while its context is unresolved:

```tsx
useRegisterView(
  "/users/detail",
  query.isPending
    ? { status: "loading" }
    : query.isError
      ? { status: "error" }
      : { context: { user: query.data } },
);
```

Loading/error publications cannot contain context. Resolve the view first,
then combine readiness for that view and its ancestors. Errors take priority
over loading. Descendant loading does not block a parent view in another
slot. Loading never triggers fallback to a different implementation.

Loading and error remain host context states, but app views render nothing in
either state. `createView` accepts only the ready `component`, with no app-provided
loading or error components. `useContext()` is available only to the ready component.

Call the hook before early returns. When using Suspense or router loaders,
publish the loading/error view from a boundary that actually mounts in that
state. A suspended component cannot publish a registration before it commits.
For Server Components, pass serializable data to a small Client Component that
calls `useRegisterView`.

## Explicit mounts

A widget or dedicated page can choose its own view independently of the current
route:

```tsx
import { Slot } from "./tailorkit-client";

<Slot.Controlled
  app={app}
  name="panel"
  view="/users/detail"
  status="ready"
  context={{ workspaceId, canManageUsers, user }}
/>;
```

Supply the complete context, including ancestor fields. This mount does not
read registered contexts or change other mounts. It renders the exact requested
view without ancestor fallback.

## Managed and controlled slots

`Slot` takes an `app` and the slot's `name`. It uses the registered view
hierarchy, including ancestor fallback and each layer's loading or error state.
For views with instances, also pass `instanceKey` to select one.

```tsx
import { Slot } from "./tailorkit-client";

<Slot app={app} name="panel" />;
```

`Slot.Controlled` renders an explicit view without reading the registered
hierarchy. Supply `view`, `status`, and the complete combined `context` when
ready, including the fields declared by its ancestors.

```tsx
<Slot.Controlled
  app={app}
  name="panel"
  view="/users/detail"
  status="ready"
  context={{ workspaceId, canManageUsers, user }}
/>
```

The controlled component renders the exact view provided; an unsupported or
unimplemented view renders nothing. It does not fall back to an ancestor.
For a view with instances, pass the selected instance object as `instance`.
For `status="loading"` or `status="error"`, omit `context` and `instance`.
Both components require `Root`, share its metadata cache, and carry the client
schema's slot and context types.

## Select an instance

Use the client-bound `useSlotInstances` hook to list instances for the matching
view and registered context. Metadata is available to the host; the app reads
its validated data with `view.useInstance()`, typed from `instances.dataSchema`.

```tsx
const { data: instances, isPending, error } = useSlotInstances({ app, slot: "panel" });

if (isPending) return <p>Loading views…</p>;
if (error) return <p>{error.message}</p>;
if (!instances?.length) return <p>No instances available.</p>;

return <Slot app={app} name="panel" instanceKey={instances[0].key} />;
```

`Slot` resolves the key and passes the selected object to the sandbox. It shows
loading, resolver errors, and missing-key states. Switching keys resets the app
view's component state. `Slot.Controlled` accepts the object directly and does
not fetch instances. Call the listing hook's `refetch()` to refresh a picker.
