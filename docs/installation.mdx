<Step title="Define the shared contract">

This file is the contract between installed apps and your platform.
It defines components, views, slots, scopes, and tool inputs and outputs. Keep this file
browser-safe: both your server and frontend import it. Action handlers and secrets belong
in the server file.

<Tip>
  Removing or changing a capability can break apps that rely on it. For example, removing a
  component makes it unavailable to every app using it.
</Tip>

<Tabs>

<Tab title="Zod">

```ts src/lib/tailorkit.ts
import { tool, defineContract } from "tailorkit";
import { primitives } from "tailorkit/zod";
import { z } from "zod";

// Define the components you want apps to use
const Button = {
  fields: z.object({
    variant: z.enum(["default", "secondary"]),
  }),
  callbacks: {
    onClick: {},
  },
  children: true,
};

export const contract = defineContract({
  // Values form the installation key: userId + teamId scopes installs per user per team.
  scopes: { user: z.object({ userId: z.string().min(1) }) },

  tools: { echo: tool.server().input(z.string()).output(z.string()) },

  components: {
    // These give apps basic layout and styling components; we strongly recommend including them.
    ...primitives({
      tokens: {
        borderColor: {
          default: "var(--border)",
        },
        textColor: {
          default: "var(--text)",
        },
      },
    }),
    Button,
  },

  // Views share page data with apps, which can provide UI for each view.
  // TailorKit shows the closest match, falling back to "/" if the app provides it.
  views: {
    "/": z.object({
      user: z.object({ id: z.string(), name: z.string() }),
    }),
  },

  // Slots define where apps render and which views they support.
  // Add dashboardActions: { views: ["/dash"] } for custom page tools.
  slots: {
    page: { views: ["/"] },
  },
});
```

<Tab title="Valibot">

Use `toStandardJsonSchema` to give Valibot schemas the JSON Schema conversion
TailorKit uses to publish your host contract. Alternatively, keep native Valibot schemas
in the contract and pass a `schemaSerializer` to `createServer`, importing the JSON Schema
converter only in the server file. The browser only requires Standard Schema validation.

```ts src/lib/tailorkit.ts
import { tool, defineContract } from "tailorkit";
import { primitives } from "tailorkit/valibot";
import * as v from "valibot";
import { toStandardJsonSchema } from "@valibot/to-json-schema";

// Define the components you want apps to use
const Button = {
  fields: toStandardJsonSchema(
    v.object({
      variant: v.picklist(["default", "secondary"]),
    }),
  ),
  callbacks: {
    onClick: {},
  },
  children: true,
};

export const contract = defineContract({
  // Values form the installation key: userId + teamId scopes installs per user per team.
  scopes: { user: toStandardJsonSchema(v.object({ userId: v.pipe(v.string(), v.minLength(1)) })) },

  tools: {
    echo: tool
      .server()
      .input(toStandardJsonSchema(v.string()))
      .output(toStandardJsonSchema(v.string())),
  },

  components: {
    // These give apps basic layout and styling components; we strongly recommend including them.
    ...Object.fromEntries(
      Object.entries(
        primitives({
          tokens: {
            borderColor: {
              default: "var(--border)",
            },
            textColor: {
              default: "var(--text)",
            },
          },
        }),
      ).map(([name, component]) => [
        name,
        {
          ...component,
          fields: toStandardJsonSchema(
            component.fields as unknown as v.BaseSchema<unknown, unknown, v.BaseIssue<unknown>>,
          ),
        },
      ]),
    ),
    Button,
  },

  // Views are URL-like paths for your product's context; apps can provide UI for each.
  // TailorKit shows the closest match, checking parent paths up to "/".
  views: {
    "/": toStandardJsonSchema(
      v.object({
        user: v.object({ id: v.string(), name: v.string() }),
      }),
    ),
  },

  // Slots define where apps render and which views they support.
  // Add dashboardActions: { views: ["/dash"] } for custom page tools.
  slots: {
    page: { views: ["/"] },
  },
});
```

<Step title="Implement the server">

Create a separate server file for server tool handlers and server configuration.
The tool inputs and return values infer from the contract.

```ts src/lib/tailorkit-server.ts
import { createServer } from "tailorkit/server";
import { contract } from "./tailorkit";

export const tailorKit = createServer({
  contract,
  baseUrl: "http://localhost:3000/api/tailorkit",
  projectKey: process.env.TAILORKIT_PROJECT_KEY,
  tools: {
    echo: ({ input }) => input,
  },
});
```

Set `baseUrl` to the full public HTTP(S) URL of your handler, including its route
prefix. It is required; relative paths are rejected. Use your public deployment
URL in production, including when requests arrive through an internal proxy.

Supply `authenticate` when calling `.handler()` to return `{ scopes, subjectId? }`. `subjectId` is any
product-defined principal, such as a user, service account, or scheduled job. Omit
it to attribute calls to the installation. Tool handlers receive verified
`context.identity`, the installation's `context.scope`, and `context.requestId`.
Authentication is required on each call to `.handler()`.

Client tools use `tool.client()` and are implemented through `createClient({
contract, tools })` in the product frontend. See [Tools](/tools) for nested callers,
backend action access, and credential behavior.

</Step>

<Step title="Create the client">

The TailorKit client connects your frontend to the TailorKit API handler and
maps the components from your contract to components in your app. It validates view
context with the original Standard Schema validators and uses their parsed output,
including stripped extra fields. The host client does not fetch `/meta`; that endpoint
remains available for app type generation.

App asset URLs normally come from discovery through `clientPath`. If you use the
deployment URL fallback, pass `assetsBaseUrl` to the client.

Create `tailorkit-client.tsx` in your frontend, wherever you keep client-side utilities.

```tsx src/lib/tailorkit-client.tsx
"use client";

import { Button } from "@/components/button";
import { contract } from "@/lib/tailorkit";
import { createClient, primitives } from "tailorkit/react";

export const tailorKitClient = createClient({
  contract,
  // Replace this with your host origin and handler path.
  baseUrl: "http://localhost:3000/api/tailorkit/",
  components: {
    ...primitives,

    Button: ({ props, children }) => (
      <Button variant={props.variant} onClick={props.onClick}>
        {children}
      </Button>
    ),
  },
});

export const {
  Provider: TailorKitProvider,
  RenderSlot,
  useApps,
  useViewContext,
  useViews,
} = tailorKitClient;

export default tailorKitClient;
```

</Step>
<Step title="Add the provider">

Wrap your pages in the TailorKit provider to use TailorKit hooks and components.
The provider uses the client that created it and renders no DOM wrapper. It accepts
`children` and an optional `apps` list; you do not need to pass `client`.

When signing in, signing out, or switching accounts, call
`tailorKitClient.fetchClient?.clear()` after updating the host auth session and
before refreshing or rendering the new auth state. This clears cached app data
and bearer tokens and invalidates pending session responses. The provider does not
detect changes to the host's auth cookie automatically.

<Step title="Render a view">

Add a page to supply view context and switch between apps available in the `page` slot.

`useViewContext(path, state)` registers the host location, context, and readiness
that app views consume. It updates when those values change and unregisters when
the component unmounts.

Its `error` field accepts a boolean, string, `Error`, or `null`. Only `false`,
`null`, and `undefined` mean no error; every string, including `""`, marks the view
as failed. An error takes precedence over `loading` and prevents context publication.

`useViews({ slot: "page" })` returns one `{ app }` item per app for single-view
slots (`multiple: false` or omitted). It checks enabled, supported app views
without calling an instance resolver or requiring registered page context. For
`multiple: true` slots, it resolves instances using the registered context and
returns `{ app, key, metadata, data }` items. Render those with
`<RenderSlot app={item.app} slot="page" instanceKey={item.key} />`.

The returned `data` items are typed from your server slot definition: instance
slots have a required `key: string`, `metadata`, and `data`; single-view slots
have only `app`. Accessing `item.key` on a single-view slot is a TypeScript error.
If the slot mode is only known at runtime, narrow an item with `"key" in item`.

Both modes support `scopes` and `appIds`. React's `useApps` and `useViews` return
only `data`, `isPending`, `error`, `isRefetching`, and `fetch()`. `isPending` is
true while the query is waiting for initial data or required context.
`isRefetching` is true during a background refresh after the initial pending
state. Call `fetch()` to request fresh data or retry an error. Cache timings are
managed by the client configuration. For single-view slots, `fetch()` refreshes
app discovery; for multiple slots, it refreshes the resolved instances.

<Tabs>

<Tab title="Next.js App Router">

```tsx app/app-views/page.tsx
"use client";

import { useState } from "react";
import { RenderSlot, useViews, useViewContext } from "@/lib/tailorkit-client";

export default function Page() {
  const [selectedId, setSelectedId] = useState("");
  const { data: views, isPending, error } = useViews({ slot: "page" });
  // Replace this with your own authentication hook.
  const { data: session, isPending: isSessionPending } = useSession();

  useViewContext("/", session ? { context: { user: session.user } } : { status: "loading" });

  const selectedView = views?.find((view) => view.app.id === selectedId) ?? views?.[0];

  if (isPending || isSessionPending) return <p>Loading views…</p>;
  if (error) return "An error has occurred: " + error.message;
  if (!selectedView) return <p>No views available yet.</p>;

  return (
    <>
      <label>
        View
        <select value={selectedView.app.id} onChange={(event) => setSelectedId(event.target.value)}>
          {views?.map((view) => (
            <option key={view.app.id} value={view.app.id}>
              {view.app.name ?? view.app.id}
            </option>
          ))}
        </select>
      </label>

      <RenderSlot key={selectedView.app.id} app={selectedView.app} slot="page" />
    </>
  );
}
```

<Step title="Verify the integration">

Start your host app, then check these endpoints at your configured host origin:

```txt
GET /api/tailorkit/schema
GET /api/tailorkit/meta
GET /api/tailorkit/apps
```

The schema and metadata endpoints describe your public app contract. The apps
endpoint requires a valid host session and returns the apps installed for the
authenticated scopes. Each scope is named by the schema key, such as `user`.

While signed in to your host, open `/app-views`. You
should see either an app view or “No views available yet.” An
unauthenticated request to `/api/tailorkit/apps` should be rejected.

If the routes return 404, check the catch-all route and handler path. If the
schema works but apps fail to load, check that `authenticate` returns a valid
session and that the client points to the same origin as your host.

</Step>
