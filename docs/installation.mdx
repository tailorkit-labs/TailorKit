Keep your setup in three files:

| File                   | Purpose                                                    | Imported by         |
| ---------------------- | ---------------------------------------------------------- | ------------------- |
| `tailorkit.ts`         | Schemas and public capability declarations                 | Server and frontend |
| `tailorkit-server.ts`  | Action handlers, authentication, and project configuration | Server              |
| `tailorkit-client.tsx` | React renderers, provider, and hooks                       | Frontend            |

<Step title="Define the shared contract">

This file is the contract between installed apps and your platform.
It defines components, views, slots, scopes, and action inputs and outputs. Keep this file
browser-safe: both your server and frontend import it. Action handlers, database imports,
authentication, and secrets belong in the server file.

Import `action` and `defineContract` from `tailorkit`, server setup from `tailorkit/server`,
and React setup from `tailorkit/react`. The contract file must not import the server file.

Omit `.input(...)` when an action takes no input; its handler receives `input: undefined`.
Omit `.output(...)` when it returns no result; its return type is `void`, or `Promise<void>`
for an async handler. Declare an output schema whenever apps need a returned value.

<Tip>
  Removing or changing a capability can break apps that rely on it. For example, removing a
  component makes it unavailable to every app using it.
</Tip>

<Tabs>

<Tab title="Zod">

```ts src/lib/tailorkit.ts
import { action, defineContract } from "tailorkit";
import { primitives } from "tailorkit/zod";
import { z } from "zod";

// Define the components you want apps to use
const Button = {
  fields: z.object({
    variant: z.enum(["default", "secondary"]),
  }),
  callbacks: {
    onClick: {},
  },
  children: true,
};

export const contract = defineContract({
  // Values form the installation key: userId + teamId scopes installs per user per team.
  scopes: { user: z.object({ userId: z.string().min(1) }) },

  actions: { echo: action().input(z.string()).output(z.string()) },

  components: {
    // These give apps basic layout and styling components; we strongly recommend including them.
    ...primitives({
      tokens: {
        borderColor: {
          default: "var(--border)",
        },
        textColor: {
          default: "var(--text)",
        },
      },
    }),
    Button,
  },

  // Views share page data with apps, which can provide UI for each view.
  // TailorKit shows the closest match, falling back to "/" if the app provides it.
  views: {
    "/": z.object({
      user: z.object({ id: z.string(), name: z.string() }),
    }),
  },

  // Slots define where apps render and which views they support.
  // Add dashboardActions: { views: ["/dash"] } for custom page actions.
  slots: {
    page: { views: ["/"] },
  },
});
```

<Tab title="ArkType">

For the scope entry, expose ArkType's `~standard` property in an object, as shown below.
This lets the current server use the scope validator while preserving its inferred types.

```ts src/lib/tailorkit.ts
import { action, defineContract } from "tailorkit";
import { primitives } from "tailorkit/arktype";
import { type } from "arktype";

// Define the components you want apps to use
const Button = {
  fields: type({
    variant: "'default' | 'secondary'",
  }),
  callbacks: {
    onClick: {},
  },
  children: true,
};

export const contract = defineContract({
  // Values form the installation key: userId + teamId scopes installs per user per team.
  scopes: {
    user: { "~standard": type({ userId: "string > 0" })["~standard"] },
  },

  actions: { echo: action().input(type("string")).output(type("string")) },

  components: {
    // These give apps basic layout and styling components; we strongly recommend including them.
    ...primitives({
      tokens: {
        borderColor: {
          default: "var(--border)",
        },
        textColor: {
          default: "var(--text)",
        },
      },
    }),
    Button,
  },

  // Views share page data with apps, which can provide UI for each view.
  // TailorKit shows the closest match, falling back to "/" if the app provides it.
  views: {
    "/": type({
      user: { id: "string", name: "string" },
    }),
  },

  // Slots define where apps render and which views they support.
  // Add dashboardActions: { views: ["/dash"] } for custom page actions.
  slots: {
    page: { views: ["/"] },
  },
});
```

<Tab title="Valibot">

Use native Valibot schemas in the contract. The server example in the next step converts
these schemas to JSON Schema for app type generation.

```ts src/lib/tailorkit.ts
import { action, defineContract } from "tailorkit";
import { primitives } from "tailorkit/valibot";
import * as v from "valibot";

const Button = {
  fields: v.object({
    variant: v.picklist(["default", "secondary"]),
  }),
  callbacks: {
    onClick: {},
  },
  children: true,
};

export const contract = defineContract({
  scopes: { user: v.object({ userId: v.pipe(v.string(), v.minLength(1)) }) },

  actions: { echo: action().input(v.string()).output(v.string()) },

  components: {
    ...primitives({
      tokens: {
        borderColor: { default: "var(--border)" },
        textColor: { default: "var(--text)" },
      },
    }),
    Button,
  },

  views: {
    "/": v.object({
      user: v.object({ id: v.string(), name: v.string() }),
    }),
  },

  slots: {
    page: { views: ["/"] },
  },
});
```

<Step title="Implement the server">

Create a separate server file for action handlers and server configuration.
The action inputs and return values infer from the contract. The `echo` action declared
above takes and returns a string. Every declared action needs an implementation, including
nested actions.

<Tabs>

<Tab title="Zod or ArkType">

```ts src/lib/tailorkit-server.ts
import { createServer } from "tailorkit/server";
import { contract } from "./tailorkit";

export const tailorKit = createServer({
  contract,
  projectKey: process.env.TAILORKIT_PROJECT_KEY,
  actions: {
    echo: ({ input }) => input,
  },
});
```

</Tab>

<Tab title="Valibot">

Import the JSON Schema converter only in this server file. `schemaSerializer` converts
schemas for `/schema` and `/meta`; browser validation uses the native contract schemas.

```ts src/lib/tailorkit-server.ts
import { createServer } from "tailorkit/server";
import { toJsonSchema } from "@valibot/to-json-schema";
import type { BaseIssue, BaseSchema } from "valibot";
import { contract } from "./tailorkit";

export const tailorKit = createServer({
  contract,
  projectKey: process.env.TAILORKIT_PROJECT_KEY,
  schemaSerializer: (schema) => ({
    ...toJsonSchema(schema as BaseSchema<unknown, unknown, BaseIssue<unknown>>, {
      target: "draft-2020-12",
      typeMode: "output",
    }),
  }),
  actions: {
    echo: ({ input }) => input,
  },
});
```

The serializer above assumes every schema in your contract is a Valibot schema.

For private action context, supply `authenticate` when creating the server. Return
`{ scopes, actionContext }`; action handlers receive the inferred `actionContext` as
`context`. Define the authentication function separately with a typed
`{ request: Request }` argument, as in the Next.js and TanStack examples, so TypeScript
can infer private context before checking the action handlers. You can also supply
authentication per request when calling `handler`.

async function handleRequest(request: Request) {
  return tailorKit.handler(request, {
    authenticate: async () => {
      // Replace this with your own authentication logic.
      const session = await auth(request);

      if (!session) {
        return null;
      }

      return {

<Step title="Create the client">

The TailorKit client connects your frontend to the TailorKit API handler and
maps the components from your contract to components in your app. It validates view
context with the original Standard Schema validators and uses their parsed output,
including transforms. Extra fields follow your schema's rules: Zod's `z.object` and
Valibot's `v.object` strip them, strict objects reject them, and loose objects retain them.
ArkType retains extra fields by default; configure its undeclared-key behavior to delete
them if needed. The host client does not fetch `/meta`; that endpoint
remains available for app type generation.

App asset URLs normally come from discovery through `clientPath`. If you use the
deployment URL fallback, pass `assetsBaseUrl` to the client.

Create `tailorkit-client.tsx` in your frontend, wherever you keep client-side utilities.
Import the contract value so TailorKit can validate context and infer types; you do not
need to import the server instance or its types.

```tsx src/lib/tailorkit-client.tsx
"use client";

import { Button } from "@/components/button";
import { contract } from "@/lib/tailorkit";
import { createClient, primitives } from "tailorkit/react";

export const tailorKitClient = createClient({
  contract,
  // Replace this with your host origin and handler path.
  baseUrl: "http://localhost:3000/api/tailorkit/",
  components: {
    ...primitives,

    Button: ({ props, children }) => (
      <Button variant={props.variant} onClick={props.onClick}>
        {children}
      </Button>
    ),
  },
});

export const {
  Provider: TailorKitProvider,
  RenderSlot,
  useApps,
  useViewContext,
  useViews,
} = tailorKitClient;

export default tailorKitClient;
```

</Step>

<Step title="Render a view">

Add a page to supply view context and switch between apps available in the `page` slot.

`useViewContext(path, state)` registers the host location, context, and readiness
that app views consume. It updates when those values change and unregisters when
the component unmounts.

`useViews({ slot: "page" })` returns one `{ app }` item per app for single-view
slots (`multiple: false` or omitted). It checks enabled, supported app views
without calling an instance resolver or requiring registered page context. For
`multiple: true` slots, it resolves instances using the registered context and
returns `{ app, key, metadata, data }` items. Render those with
`<RenderSlot app={item.app} slot="page" instanceKey={item.key} />`.

The returned `data` items are typed from your server slot definition: instance
slots have a required `key: string`, `metadata`, and `data`; single-view slots
have only `app`. Accessing `item.key` on a single-view slot is a TypeScript error.
If the slot mode is only known at runtime, narrow an item with `"key" in item`.

Both modes support `scopes` and `appIds`. React's `useApps` and `useViews` return
only `data`, `isPending`, `error`, `isRefetching`, and `fetch()`. `isPending` is
true while the query is waiting for initial data or required context.
`isRefetching` is true during a background refresh after the initial pending
state. Call `fetch()` to request fresh data or retry an error. Cache timings are
managed by the client configuration. For single-view slots, `fetch()` refreshes
app discovery; for multiple slots, it refreshes the resolved instances.

<Tabs>

<Tab title="Next.js App Router">

```tsx app/app-views/page.tsx
"use client";

import { useState } from "react";
import { RenderSlot, useViews, useViewContext } from "@/lib/tailorkit-client";

export default function Page() {
  const [selectedId, setSelectedId] = useState("");
  const { data: views, isPending, error } = useViews({ slot: "page" });
  // Replace this with your own authentication hook.
  const { data: session, isPending: isSessionPending, error: sessionError } = useSession();

  useViewContext("/", {
    context: session ? { user: session.user } : undefined,
    loading: isSessionPending,
    error: sessionError,
  });

  const selectedView = views?.find((view) => view.app.id === selectedId) ?? views?.[0];

  if (isSessionPending) return <p>Loading your session…</p>;
  if (sessionError) return <p>Unable to load your session.</p>;
  if (!session) return <p>Sign in to view installed apps.</p>;
  if (isPending) return <p>Loading views…</p>;
  if (error) return <p>Unable to load views: {error.message}</p>;
  if (!selectedView) return <p>No views available yet.</p>;

  return (
    <>
      <label>
        View
        <select value={selectedView.app.id} onChange={(event) => setSelectedId(event.target.value)}>
          {views?.map((view) => (
            <option key={view.app.id} value={view.app.id}>
              {view.app.name ?? view.app.id}
            </option>
          ))}
        </select>
      </label>

      <RenderSlot key={selectedView.app.id} app={selectedView.app} slot="page" />
    </>
  );
}
```

<Step title="Verify the integration">

Start your host app, then check these endpoints at your configured host origin:

```txt
GET /api/tailorkit/schema
GET /api/tailorkit/meta
GET /api/tailorkit/apps
```

The schema and metadata endpoints describe your public app contract for app tooling.
The host React client uses the imported contract and does not request these endpoints. The apps
endpoint requires a valid host session and returns the apps installed for the
authenticated scopes. Each scope is named by the schema key, such as `user`.

While signed in to your host, open `/app-views`. You
should see either an app view or “No views available yet.” An
unauthenticated request to `/api/tailorkit/apps` should be rejected.

If the routes return 404, check the catch-all route and handler path. If the
schema works but apps fail to load, check that `authenticate` returns a valid
session and that the client points to the same origin as your host.

## Separate backend and frontend repositories

Put `tailorkit.ts` in a shared package that both repositories can import. For example,
`@your-product/tailorkit-contract` can export `contract` and depend on `tailorkit` and your
schema library. Build and publish that package as part of your normal release process.

The Hono backend imports that contract in `tailorkit-server.ts` and exposes the TailorKit
handler. The Next.js frontend imports the same contract in `tailorkit-client.tsx` and
points `baseUrl` at the backend's handler. Only the backend needs the project key, action
implementations, authentication, and JSON Schema conversion.

A separate repository does not require a separate browser origin. For cookie-based
sessions, serve or proxy the backend's TailorKit route under the frontend's origin.
For a direct cross-origin connection, configure CORS on the backend and provide a client
`fetch` implementation that includes the credentials your backend requires. Keep both repositories on
compatible contract versions. Installed app tooling can still use the backend's
`/api/tailorkit/meta` and `/api/tailorkit/schema` endpoints for type generation.
