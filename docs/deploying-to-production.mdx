Best practices for deploying TailorKit to production, including data sharing,
input validation, authorization, and UI security.

## Best practices

### Share only the data apps need

Apps can read every field you share through `useRegisterView()`. Pass a small view
model without raw database records, sessions, access tokens, or route-loader objects.

### Validate component fields

Use enums, bounded numbers, booleans, and structured objects. Validate link `href`
and media `src` values before rendering. Allow only the protocols each component
needs: usually `https:` for media and `https:` or `mailto:` for links.

Render text as text. Sanitize any raw HTML you support.

### Keep callbacks for UI events

Use callbacks such as `onClick`, `onOpenChange`, and `onValueChange` to notify apps
of UI interactions. Use host-owned server actions for API calls, data changes,
billing, authentication, invites, role changes, and other side effects.

### Authorize every action

Check identity and permissions on the server using authenticated host `context`,
regardless of which controls the UI shows. Validate action inputs and outputs,
scope database queries to the authenticated tenant, and return only the data the
app needs, without secrets or internal metadata.

### Scope app installations

Define stable `scopes` schemas, such as `user` and `organization`. In `authenticate`,
return values under the same names from the signed-in session, rather than app
requests. Use stable opaque IDs; TailorKit receives them to match and display
installations.

Keep project keys and CLI credentials on the server or developer machine, outside
browser bundles and app context.

### Keep your design system in control

Use TailorKit primitives and theme tokens. Avoid raw class names, HTML, and
unrestricted `style` objects; constrain every style property and value you expose.

Keep destructive, billing, authentication, invite, role, and permission controls
recognizable as host-owned UI. Apps should not visually replace these flows.

See the [installation guide](/installation) for the host configuration,
authentication handler, and primitive setup.

## URL validation examples

These examples allow HTTPS and email links. For media sources, allow only `https:`.

<CodeGroup>

```ts Zod
import { z } from "zod";

const Link = {
  fields: z.object({
    href: z.url({ protocol: /^(https|mailto)$/ }),
  }),
};
```

```ts ArkType
import { type } from "arktype";

const Link = {
  fields: type({
    href: type("string.url").narrow((href) =>
      ["https:", "mailto:"].includes(new URL(href).protocol),
    ),
  }),
};
```

```ts Valibot
import * as v from "valibot";
import { toStandardJsonSchema } from "@valibot/to-json-schema";

const Link = {
  fields: toStandardJsonSchema(
    v.object({
      href: v.pipe(
        v.string(),
        v.url(),
        v.check((href) => ["https:", "mailto:"].includes(new URL(href).protocol)),
      ),
    }),
  ),
};
```

</CodeGroup>
